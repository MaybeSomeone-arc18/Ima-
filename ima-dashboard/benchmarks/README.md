# Retrieval benchmark (manual)

From `ima-dashboard`, set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` for a database with populated article embeddings, then run `npm ci && npm run benchmark:retrieval -- 5`. The script does read-only queries, but each linear run fetches the full article table. Use a staging copy for repeatable comparisons; do not commit keys or benchmark data.

It picks the first stored article vector as a fixed query, warms both paths once, alternates their order over 1-20 measured rounds, and prints median wall-clock milliseconds, corpus size, vector dimensions and top-five overlap. This times only retrieval. It excludes Gemini embedding, answer generation, ingestion and browser UI. Linear includes paginated PostgREST transfer plus JS cosine/sort; indexed includes the `match_articles` RPC and Postgres response. That is a comparison of *application paths*, not isolated HNSW versus exact-scan CPU time. Check `EXPLAIN (ANALYZE, BUFFERS)` in Postgres if the query plan itself matters: small tables may not use the HNSW index. Cache, network, table changes, ties and ANN approximation affect results; report the corpus, setup and raw output rather than claiming a general speedup. If the RPC fails, `db.js` currently returns an empty result and logs an error: treat zero indexed hits as invalid, not a performance result.
